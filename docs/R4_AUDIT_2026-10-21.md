## 4. Critical findings

### 4.1 Integrity risks (fix before anything goes in the report)

**(a) The eval is simulated, but it's presented as real model results.**
- `eval/run_eval.py:75-109`, `run_model_simulation()`: the prediction is `r["ground_truth"]` (line 98), i.e. the label is copied into the prediction. The only "errors" are two hardcoded `if finding_id == "gt-004"/"gt-006"` branches.
- The `model_name` parameter is never used, so "Llama 3.1 8B" and "Qwen 14B" rows are identical by construction.
- No LLM is called anywhere in `eval/`.
- `docs/REPORT_DRAFT_SECTIONS_7_9.md` §9.2 presents this as a bake-off. `docs/AI_DISCLOSURE.md` row 10 says *"Ollama (Qwen2.5-Coder 14B) | eval/run_eval.py | Model bake-off…"*.
- **Why it's serious:** the panel can open `run_eval.py` in 30 seconds. PLAN rule 1 is *"Honest evaluation"*. This is the 20% "LLM triage soundness" criterion.

**(b) The ablation table shows the opposite of what it claims.**
- `evaluate_predictions()` counts `hallucinated_cves` only from the validator's `rejected_claims` (`run_eval.py:21-25`). With the validator off, there are no rejections, so the row shows **0** hallucinated CVEs. The report then says that row *"allows hallucinated CVEs to leak"*. The metric should count hallucinated CVEs *present in the output that reaches a human* (leaked), not CVEs rejected.
- The "without JSON grammar" row has precision/recall 1.0, the same as the full system, so it demonstrates nothing.

**(c) The PR review notes carry teammates' names, but there are no teammate reviews.**
- `ai/pr_bot.py:34-38, 57-61, 86-90` hardcode `"reviewer": "R3 (Container & Supply Chain)"`, `"R2 …"`, `"R1 …"` with text like *"Hadolint passes with zero warnings"*, *"Trivy scan passes"*, *"Checkov … zero violations"*.
- None of those scans can have run, because the target files don't exist: `docker/` is empty, `infra/` is empty, `apps/vulnshop-api/` is empty.
- TEAM_RESPONSIBILITIES is explicit: *"R1/R2/R3 review and write the review notes. Their names go on the graded artefact."* This row exists so the review notes are authentic.

**(d) The "AI-generated" PRs weren't generated by AI.**
- `pr_bot.py` has no import of `llm_client` and never calls a model. The four diffs are string literals. The `model` / `prompt_version` fields are labels, not provenance.
- The patches are also technically broken:
  - PR-001: `FROM node:20.11.1-alpine@sha256:d4e3b7b89...` is a truncated digest, so the Dockerfile is invalid. The hunk header `+1,8` should be `+1,7`. It also has a pointless `-CMD/+CMD` identical-line change.
  - PR-002: targets `package.json` (Node), but PR-004 targets `routes/search.py` (Python) in the same `vulnshop-api`, so the service language is inconsistent. **Check CVE-2022-23529:** to my knowledge that jsonwebtoken advisory was **withdrawn/disputed** by its CNA in early 2023. Verify against NVD/GHSA before citing it. Your own validator would reject it, because it isn't in `OFFLINE_KNOWN_CVES`. jsonwebtoken 8→9 is also a breaking major (algorithm / key-size defaults changed), so *"no breaking changes"* is unlikely to be true.
  - PR-003 / PR-004: the hunk line counts don't match their bodies, so `git apply` would reject them.

**What "fixed" looks like for (a)–(d):** see §6, items 1–4.

### 4.2 The grounding validator validates the wrong thing

`ai/validate.py`

1. **It checks scanner input, not model output.** Lines 53 and 59 read `finding["cwe"]` and `finding["cve"]`. Those come from the *scanner*, not the model. The triage prompt schema (`triage_v1.txt:22-29`) doesn't even give the model a CVE/CWE field. The only place the model can make a factual claim is the free-text `fix_summary`, and that is **never checked**. Probe: `fix_summary: "Upgrade to fix CVE-2031-12345"` → `validated = True`. As built, the headline *"the model proposed N CVEs that don't exist; zero reached a human"* can't be measured.
2. **Any missing file passes** (lines 40-41): `return not file_path.startswith("nonexistent") and ".." not in file_path`. That condition matches the self-test's fixture name. Probe: `made/up/file.py:99999` → `validated = True`. Since `apps/` is empty, *every* location in the eval currently passes.
3. **Line bounds have +10 slack** (line 37: `total_lines + 10`).
4. **The CWE allowlist is 26 IDs.** Probe: CWE-1021, CWE-1333, CWE-117 and CWE-601 are all real and all rejected. That causes the gt-010 false abstain in the real run.
5. **The CVE registry is 7 hardcoded IDs.** Any real Trivy run on Juice Shop will produce hundreds of valid CVEs. They'd only survive through `raw_cve`, which **no producer sets** (it isn't in the schema).
6. PLAN §4.3 also requires checking **package+version against the SBOM** and **fix version against registry data**. Neither is implemented.

**Fix direction:**
- Have the model emit structured claims: `{"cves":[], "cwes":[], "fixed_version": null, "file":..., "line":...}` alongside the verdict.
- Run a regex extraction of `CVE-\d{4}-\d+` / `CWE-\d+` over `fix_summary` as well.
- Validate claims against (i) the raw scanner record for that finding, (ii) the offline MITRE CWE XML (~1,000 IDs, a 2 MB file you can commit), and (iii) an offline OSV/NVD snapshot or the CVE list.
- Any missing file means **reject**.
- Log every rejection to `artifacts/llm_trace/rejections.jsonl`.

### 4.3 Redaction: claimed as verified, but leaky

`ai/redaction/redactor.py`, probe results:

| Input shape | Leaked? |
|---|---|
| AWS **secret** access key (`wJalrXUtnFEMI/K7MDENG/…`) | ❌ leaked |
| Unquoted password `password=SuperSecretPassw0rd!2024` | ❌ leaked (the regex requires quotes and 16+ chars from `[A-Za-z0-9_.-]`) |
| GitHub fine-grained PAT `github_pat_…` | ❌ leaked |
| Slack bot token `xoxb-…` | ❌ leaked |
| GCP API key `AIza…` | ❌ leaked |
| base64-wrapped AWS key | ❌ leaked |
| Secret split across lines | ❌ leaked |
| Unicode homoglyph AKIA (Cyrillic І) | ❌ leaked |
| Internal hostname `payments-db.internal.corp` | ❌ leaked |
| IPv6 address | ❌ leaked |
| DB connection string with password | ⚠️ redacted *by accident* (the email regex ate `hunter2pass@db.internal.corp`) |
| `lodash 4.17.21.0` | ⚠️ **over-redacted** as an IP |

All of these are in PLAN §4.5's required fixture list (*"AWS/GCP keys, JWTs, PEM blocks, base64-wrapped secrets, secrets split across lines, Unicode homoglyphs"*).

Further issues:
- **No entropy scan**, though PLAN L2 says "gitleaks rules as a library + entropy scan".
- **Raw secrets leak into the triage output.** `triage.py:73` does `final_output = rep.copy()`. That's a shallow copy of the *unredacted* finding, so `evidence.snippet_raw` goes straight into the result that feeds PR comments and dashboards. Confirmed in the real run (10/10 records). The redaction protects the model but not the human-facing surfaces. Also, line 80 mutates `rep["evidence"]` through the shared reference.
- **The L4 canary is designed backwards.** `apply_l4_canary()` appends `_canary: CANARY_TOKEN` to the payload, so the canary is *guaranteed* to reach the model (probe: `canary in user prompt sent to model: True`). A canary tripwire works the other way round. You plant canary values *disguised as secrets* in the input (e.g. `AKIA` + canary suffix, `password="CANARY_…"`, a canary email), then assert they are **absent from the outbound prompt** (a pre-egress hard stop in code) and absent from the proxy log. The current output-side check only detects the model *echoing* a token you deliberately gave it.
- **L1 drops `message`, which is good, but it keeps `rule_id` and `file_name` verbatim.** Both are attacker-controllable strings, since file names are chosen by the committer.
- The report says L3 strips "internal IP addresses (RFC 1918)". The regex matches *any* dotted quad, including version strings.

### 4.4 The egress guard can be bypassed

`redactor.py:69-79`:
```python
allowlist = ["http://localhost", "http://127.0.0.1"]
if url.startswith(allowed): return True
```
Probe: `http://localhost.evil.com/v1` → **allowed**, `http://localhost@evil.com/v1` → **allowed**, `http://127.0.0.1.nip.io/v1` → **allowed**.

On top of that, both the SDK and urllib honour `HTTP(S)_PROXY` env vars, so even a correct hostname check can be routed elsewhere. Also nothing is logged, so there's no "egress log" artefact for the final checklist.

**Fix:** `urllib.parse.urlsplit(url)`; require `scheme in {"http","https"}`, `hostname in {"localhost","127.0.0.1","::1"}` exactly, and no userinfo. Resolve the host and assert it's loopback. Clear proxy env vars for the client. Then, for simulated-cloud mode, put a real deny-by-default proxy in front (mitmproxy or tinyproxy in Docker with one allowlisted upstream). Log `ts, host, sha256(body), allowed/denied` to `artifacts/evidence/egress/egress.log`.

### 4.6 Other module issues

- **`llm_client.py`**
  - The exception text goes into `fix_summary` and `rejected_claims` (line 64-65). That's harmless locally, but it's an info-leak pattern.
  - The client is created at import time.
  - There's no retry.
  - It uses `json_object` mode, not a schema. Ollama's native `/api/chat` accepts `"format": <JSON Schema>` for real grammar-constrained decoding. Use that so the "without grammar" ablation is meaningful.
- **`cluster.py`:** clustering by basename makes `apps/a/index.js` and `apps/b/index.js` collide (probe: 1 cluster). Use the full normalised path. It also relies on `rule_id`, which isn't in schema v1.
- **`enrich.py`**
  - EPSS-by-CWE isn't a real thing. Drop it, or rename it to a documented internal prior.
  - Hardcoded `reachable: True` should be `null` / unknown until implemented. Claiming reachability you don't compute is the same failure mode the validator exists to prevent.
- **`models.lock.yaml`:** placeholder digests. Fill them from `ollama show <model> --modelfile` / `ollama list`. Add `license`, `license_osi_approved`, `source_url`.
- **Prompts:** the `eval_score` values ("F1: 1.0", "Accuracy: 95%", "Conciseness: 100%") have no eval behind them. Set them to `"not yet evaluated"` until a real run produces a number. `triage_v1.txt` lacks front-matter.
- **`tests/`**
  - `test_defense_routing_to_needs_human_review` puts the defence logic *inside the test*, so it's tautological.
  - Nothing tests `triage.py`, `validate.py` or `cluster.py`.
  - `test_egress_guard` passes while the guard is bypassable. Add the three bypass URLs as negative cases.

## 9. Additional things worth doing (beyond the plan)

7. **`hypothesis` property test** for the redactor: generate random code + an embedded secret from N generators, assert the secret never survives, and measure over-redaction on secret-free code.
8. **Prompt regression with `promptfoo`** (listed in PLAN §8): a declarative matrix of prompts × models × fixtures, which can run in CI on prompt-file changes.
9. **Injection corpus:** go beyond one payload. Add 15–20 variants (unicode-obfuscated, base64, split across comment lines, in file names, in rule messages) and report detection rate + false-alarm rate on benign code.
