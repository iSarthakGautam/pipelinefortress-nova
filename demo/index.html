Our four rules

① Honest evaluation, held-out by time.
② The LLM never acts: it suggests, a human merges.
③ Nothing sensitive leaves the runner.
④ Every AI use is disclosed.

The trap

A naive "fail on any HIGH" gate on an app like Juice Shop is red on every pull request, so the team switches it off within a week. Our gate has to be one people keep on.

"The CISO's problem: thirty deploys a day, one review a sprint. They want eighty percent of bugs caught before merge. The trap is the gate: if it's red on every PR, developers turn it off. So the design question isn't 'can we scan', it's 'can we build a gate people leave on, and an AI that can't be turned against us'."

Station 7 · Security gate

The file stops here. Merge blocked.

❌ Security Gate FAILED · 1 new HIGH · semgrep sql-injection · search.py:42

What decides

One number: the exit code of the baseline check. A deterministic script. Fail-closed: a missing file or a skipped job is a failure.

What does not decide

The AI stage. If the model is down, wrong, or hijacked, the verdict is the same. It can neither block nor unblock a merge.

ATTACKER
cancel / skip the scan job
🛡FAIL CLOSED
STILL RED
GitHub treats a skipped job as passing; our gate runs on !cancelled() and fails unless the baseline job succeeded.
"The file stops at the gate, because it contains a new high-severity finding. What decides is one deterministic exit code. What does not decide is the AI: if the model is down, wrong or hijacked, the answer is the same. The bad actor's last trick here is to cancel or skip the scan so the job shows as skipped, which GitHub counts as passing. Our gate runs even when cancelled and fails unless the scan job actually succeeded."
Second push · the fix

A fix arrives. The AI drafts it. A human decides.

-q = f"SELECT * FROM items WHERE name = '{user_input}'"
-cursor.execute(q)
+q = "SELECT * FROM items WHERE name = ?"
+cursor.execute(q, (user_input,))

How the bot works now

The model returns the whole file; code computes the diff. Before: model wrote the diff, 0 of 4 applied. Now: 4 of 4 apply.

"Applies" isn't "correct"

A first run "applied" garbage because the model echoed our data wrapper. Now it's unwrapped or refused, and lines changed is shown.

v2 batch · 4 patches apply cleanly

Draft PRs · label ai-drafted · review: pending a human. Nothing merges on "applies".

v1 · PR-003 · lodash → 4.17.21

Rejected by a human (R2): patch didn't apply, and that version still has open advisories; target ≥ 4.18.0.

"A fix arrives. Our bot can draft these, but with a rule: it's a draft pull request that a human decides on. We had a real failure here: the model wrote the diff and none of the four patches applied, because models can't count hunk lines. So now the model returns the whole file and code computes the diff. All four apply. But applying isn't correct, so people review them, and we show a rejection on purpose: the lodash bump the model was asked for still has open advisories. A rejected AI PR with a sharp reason is stronger evidence than four accepted ones."

Scope, limits and what comes next

Evaluation

Smoke set of 10 rows today. The real 98-issue set is frozen and goes to two independent reviewers next (tools and sheets are ready).

The model

Confidently wrong twice on 10. The validator catches unproven claims, not wrong judgement.

Pipeline

DAST is advisory and passive. The container, kind and policy stages are advisory until their first green runs. Falco, signing and admission control are out of scope.

Bias

We knew what we planted and tuned rules against it. Lab, not production.

"Four honest limits. Our evaluation set is small and I labelled my own synthetic rows; the real set is frozen but needs two independent labellers. The model is confidently wrong sometimes, and a validator can't catch bad judgement. Some stages are advisory and haven't had their first green run.
